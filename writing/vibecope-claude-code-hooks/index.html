The hook is plumbing, the server is the brain

Lessons from building Vibecope, a macOS app that coaches Claude Code prompts in real time — and the architecture rule that kept it honest.

The premise

Most disappointing agent sessions start the same way: a vague prompt. "Fix the layout" — which layout? Which file? Compared to what? Coding agents are spectacular at execution and obedient to a fault, so a fuzzy instruction gets a confident, fuzzy result.

There are tools that evaluate prompt clarity, but they're stateless — they judge one message in a vacuum. The interesting problem is stateful coaching: knowing what you said three messages ago, what this project is about, and which vague phrases you personally tend to repeat.

One brain, not two

Claude Code exposes lifecycle hooks, including UserPromptSubmit: a script that runs on every prompt before the model sees it, and whose output can be injected into context as additionalContext. That's the entire integration surface Vibecope needs.

The early temptation was to put intelligence in the hook — local heuristics, regex checks, word counts — and only escalate hard cases to an LLM. I scrapped that. A local heuristic isn't beating a small LLM with retrieval, and two evaluation systems disagreeing is worse than one. The rule that crystallized:

The hook is plumbing. The server is the brain. One brain, not two.

The hook is ~70 lines: read stdin, POST to localhost:7483, print the response. Every decision lives server-side, where it can be tested, versioned, and improved without touching the integration.

Three layers of context

A single prompt is ambiguous; a prompt with history usually isn't. The server assembles three layers before judging anything:

LayerSourceFailure it prevents
Current conversationThe session transcript, passed by the hookFlagging "make it bigger" as vague when the referent was named two turns ago
Project historyRAG over SQLite, filtered by project pathThe "134th message" problem: you switch back to Project A after a week on Project B, and recency-based context is all wrong
Cross-project patternsRAG across all projectsMissing that "text is too big" always means "fix the line-height" for this user

Retrieval priority follows that order: current conversation beats same-project history beats cross-project patterns. Embeddings run locally via ONNX — no vector database, no API dependency for retrieval — because the product constraint was zero-config install.

The 500ms rule

A coaching tool that adds latency to every prompt gets uninstalled by lunch. So degradation is graceful at every layer:

  • The hook times out at 500ms. Server down? The prompt passes through untouched, silently.
  • The server caps its LLM call at 2s. Slow? Return green now, analyze asynchronously, learn for next time.
  • Evaluation always runs on a small, fast model (Haiku) regardless of what model the user codes with. One cheap call per prompt.

The user never waits for the feature. Ever. That single constraint shaped more of the architecture than any modeling decision.

The feedback loop nobody sees

Every prompt and its verdict are logged. When the next prompt arrives, it updates the previous record's next_prompt field — so the system can ask, retroactively: after we coached, did the user's follow-up actually get clearer? That's the difference between a linter and a coach: a coach checks whether the advice worked.

Takeaways

  • Put intelligence where you can iterate on it. Hooks, extensions, and plugins should be dumb pipes; brains belong behind an interface you control.
  • Statefulness is the moat. Anyone can call an LLM on a string. Memory across sessions is what makes the call worth making.
  • Latency budgets are product decisions. Decide what happens when you blow the budget before you build the feature.
